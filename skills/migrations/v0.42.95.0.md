# v0.42.95.0 - swallowed argument rejected on add_timeline_entry

`add_timeline_entry` takes `summary`, `detail` and `source` as separate
arguments. An agent that makes a formatting slip can serialize one of them into
the end of another, so `detail` ends with `<parameter name="source">value` and
`source` arrives empty. GBrain used to store that verbatim and reply `ok`, which
is the same reply it gives for a write that changed nothing, so the calling
agent never learned it had gone wrong.

The write is now rejected with `invalid_params`. The error names the swallowed
parameter, quotes the value it recovered, and states that nothing was written.
The check runs before the dry run short circuit, so a preview surfaces it too.

## No schema migration

Nothing to apply. There is no DDL in this release.

## What the agent should do after upgrading

1. **Count whether this brain already carries entries written that way.** The
   guard stops new ones; it does not repair old ones.

   ```sql
   SELECT count(*) FILTER (WHERE summary ~ E'<parameter\s+name="[A-Za-z_][A-Za-z0-9_.-]*"\s*>[^<]*$') AS summary_hits,
          count(*) FILTER (WHERE detail  ~ E'<parameter\s+name="[A-Za-z_][A-Za-z0-9_.-]*"\s*>[^<]*$') AS detail_hits,
          count(*) FILTER (WHERE source  ~ E'<parameter\s+name="[A-Za-z_][A-Za-z0-9_.-]*"\s*>[^<]*$') AS source_hits
   FROM timeline_entries;
   ```

   All zeros means there is nothing to do and this migration is finished.

2. **Read every match before changing it.** Some matches are entries that quote
   this markup on purpose to document the problem. Those are correct records and
   repairing them destroys the evidence. Tell them apart by the companion field:
   a genuinely damaged row has an EMPTY `source` (or an empty `detail`) where the
   swallowed value belongs. A row that merely discusses the markup has both
   fields populated.

3. **Back up the table before any repair, and repair one shape at a time.**
   There is more than one shape and a single pattern gets them wrong. A value
   glued onto the end of a field is removed from that field and moved into the
   empty one. A whole field body that landed in `summary` while `detail` is zero
   bytes is moved wholesale. Verify the destination field is empty first, so
   nothing is overwritten.

4. **Re-check the counts after repairing.** Re-run the query in step 1. Any
   remaining `summary` or `source` hit after a repair means new corruption
   arrived, which would mean the guard is not running in the process that served
   the write.

## What does NOT change

`put_page` is not guarded. The same query run against the `pages` table returned
zero on the brain where this was measured, so the check stays on the operation
where the corruption actually happens rather than being sprayed across every
write path.

Entries whose stray tag sits in the MIDDLE of a field rather than at its end are
not matched and never were. Truncating at the marker would delete real content
there, so those need per row judgement rather than a transform.
