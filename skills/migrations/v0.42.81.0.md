# v0.42.81.0 — entity_dirs safety guard

`link_resolution.entity_dirs` declares which top-level folder names the link
extractor recognizes in references. It reads like a coverage setting. It is also
a safety setting: a folder name that is not declared is not extractable, so
references under it never produce links, existing links stop being reconciled,
and for some reference shapes those existing links are removed. The `links`
table has no tombstone column, so a removal cannot be undone.

v0.42.80.0 added a removal safety net (`unresolvableRefs`) that holds back a
removal when the body still carries an unresolvable reference to the target.
**That net covers the generic wikilink shape only.** A reference under an
undeclared folder written as a markdown link (`[x](sessions/foo)`), as a bare
slug (`sessions/foo`), or as a qualified wikilink (`[[wiki:sessions/foo]]`)
produces no ref at all, never reaches `unresolvableRefs`, and is still removed.
Verified by probe against the merged extractor.

> **Superseded in v0.42.84.0.** The net now covers all four reference shapes, so
> the three listed above are no longer removed. If you are upgrading to v0.42.84.0
> or later, treat the paragraph above as history: you do NOT need to declare a
> folder name to stop the deletion. Everything else in this file still applies,
> because declaring the folder name is still what makes those references produce
> links and stay reconciled in the first place.

So the two mechanisms are complementary. The net stops the deletion. Declaring
the folder name is what keeps links being created and kept current at all.

This release surfaces that property. No schema migration is applied.

## What changes for an existing brain

1. **`gbrain doctor` can now report `fail` where it previously reported clean.**
   The new `entity_dirs_orphaned_edges` check fails when links exist whose
   reference sits under a folder name the current setting does not declare.
   Those links have already stopped being reconciled, and the ones whose
   reference is not a generic wikilink are one `put_page` away from deletion.

   **This is the part that needs attention if you gate automation on
   `gbrain doctor`'s exit code.** A cron or CI step that treats a non-zero
   doctor as an outage will start firing on a brain that has stranded links.
   That signal is correct and the fix is one command, but it can arrive
   unannounced.

2. **`gbrain config set link_resolution.entity_dirs` and
   `gbrain config unset link_resolution.entity_dirs` now refuse** a change that
   would strand existing links. Scripts that narrow this setting
   non-interactively need `--yes` added, or they will exit 1 and change
   nothing. Adding folder names, and removing folder names that nothing depends
   on, are unaffected.

## What the agent should do after upgrading

1. **Run the check:**
   ```bash
   gbrain doctor
   ```
   Look for `entity_dirs_orphaned_edges`. If it is `ok`, there is nothing to do
   and the rest of this file does not apply.

2. **If it reports `fail`, read what it found before acting.** The message
   carries the number of links at risk, the number of pages affected, a
   breakdown per folder name, and up to five example `page -> target` pairs.
   Confirm the example pages really do reference those folders.

3. **Apply the printed remedy.** The check prints a ready to paste command that
   re-sets the whole list, not just the missing names:
   ```bash
   gbrain config set link_resolution.entity_dirs '<full list from the message>'
   ```
   Use the printed list verbatim. Setting only the missing folder names would
   drop the ones already declared and strand a different set of links.

4. **Re-run `gbrain doctor`** and confirm the check now reports `ok`.

5. **If any automation narrows this setting**, add `--yes` to those call sites
   after confirming the loss is intended.

## Notes

- `GBRAIN_LINK_RESOLUTION_ENTITY_DIRS` takes priority over the stored setting,
  so a shell that exports a shorter list bypasses the `config set` refusal. The
  doctor check reads whichever value is in effect, so it still reports the
  problem in that case. Prefer the stored setting over the environment variable
  for anything long lived.
- `link_resolution.global_basename` is not a mitigation. In that mode a
  reference under an undeclared folder is matched by name, but it is recorded
  as a different kind of link, so the original link is still removed.
- The check only reports a folder name when a real link depends on it. A
  reference to a page that was never linked is not reported, because there is
  nothing to lose.
